## 1. 项目一句话

基于 Python + Pytest 的**企业级电商全平台自动化测试框架**：四层架构（驱动/PO/服务/用例）+ 数据驱动 + 失败即证据 + AI 工具链 + 质量工程平台（门禁/看板/失败聚类/定时回归）+ GitHub Actions CI。

**技术栈**：pytest 9 · Selenium/Playwright · Appium/Airtest · requests · Allure · Flask + SQLite · loguru · GitHub Actions

---

## 2. 分层架构（面试必答）

```
用例层 tests/          断言 + 数据驱动（parametrize）+ marker 分层（smoke/api/ui...）
服务层 service_objects 组合 PO 实现业务流（登录→下单），记录步骤日志，不写断言
页面层 page_objects    PO 模式：元素定位器集中 + 页面操作，不写断言
通用层 utils/          驱动生命周期（drivers）+ 日志/配置/路径/API（tools）+ AI 工具链（ai）
数据层 config/*.yaml  多环境配置 + ${VAR} 环境变量覆盖；test_data/*.yaml 测试数据
```

**核心约束**：元素变只改 PO、业务变只改 SO、断言只留用例层 → 维护成本最低。

## 3. 大厂向核心设计（面试亮点）

### 3.1 失败即证据（稳定性治理核心）

| 能力 | 实现 |
| :--- | :--- |
| 失败自动截图 | `pytest_runtest_makereport` hook：call 阶段最终失败时截图（兼容 Selenium `get_screenshot_as_png` / Playwright `screenshot()`），落盘 `reports/screenshots/` + attach Allure |
| 失败自动重试 | `--reruns=1 --reruns-delay=1`；重试中的失败（outcome='rerun'）**不截图**，最终失败才截图 |
| flaky 标记 | 曾失败但重试通过的用例 → Allure 附件标记 + `reports/flaky_rerun.json` 记录（flaky 治理第一手信号） |
| Playwright trace | session 级录制（录屏+DOM 快照+网络），存 `reports/traces/` |

### 3.2 AI 工具链（utils/ai/）

| 模块 | 能力 | 无 Key 降级 |
| :--- | :--- | :--- |
| `llm_client.py` | OpenAI 兼容对话（通义/DeepSeek/OpenAI/本地 vLLM），Key 走环境变量 `LLM_API_KEY/LLM_BASE_URL/LLM_MODEL` | available=False |
| `failure_analyzer.py` | 失败归因四分类（产品缺陷/测试缺陷/环境波动/定位器失效）+ 置信度 + 建议 | 规则引擎（异常类型关键词映射） |
| `flaky_detector.py` | 最近 N 次失败率 30%~70% → 疑似 flaky（业界标准区间） | 纯计算 |
| `test_generator.py` | 描述 → pytest 用例骨架（API/UI） | 输出模板 |

### 3.3 质量工程平台（quality_platform/，替代旧 web_platform）

```
Flask + SQLite（零运维），启动：python -m quality_platform.app → :8081
├─ 看板 /         质量门禁(PASS/WARN/FAIL 卡发布) · 质量分(0~100) · 通过率/flaky率 · 趋势图 · 测试金字塔
├─ 失败分析 /failures 截图证据 · AI 归因 · 失败指纹聚类（同根因 N 个失败） · flaky 识别
├─ 执行中心 /runs  参数化执行（并发 -n/重试 --reruns/超时/marker） · 执行详情 · 定时任务（nightly 回归）
└─ 用例清单 /cases pytest --collect-only 实时收集
```

- **质量门禁**：`config/platform_config.yaml` 阈值（min_pass_rate 80 / max_fail 5 / max_flaky 0.3）→ 最近执行评估 FAIL/WARN/PASS，FAIL 阻止发布
- **质量分**：通过率 60% + 稳定性 30% + 执行覆盖 10%
- **失败指纹聚类**：error_type + 错误信息前 60 字符规范化（去数字/hex）→ md5 聚簇，识别同根因
- **执行环境注入**：`exec_env` 配置注入 pytest 子进程（${VAR} 透传宿主环境变量）

### 3.4 稳定性规范（面试高频）

1. **禁 sleep 硬等待**：显式等待（WebDriverWait / wait_for_selector 轮询+超时）
2. **定位器契约**：优先语义化（placeholder/role/data-testid），禁 nth-child
3. **重试克制**：1~2 次，>2 掩盖真实缺陷
4. **flaky 治理闭环**：识别（30%~70%）→ 隔离（不阻塞主干）→ 限时修复 → 归档
5. **环境/数据隔离**：`.env` 敏感信息零入库，CI 用全新环境 + 种子数据

## 4. 高频面试问答（速记版）

**Q: PO 模式是什么？为什么用？**
将页面抽象为类：元素定位器 = 类属性，操作 = 类方法。好处：复用（登录一次封装多处用）、隔离变更（元素变只改 PO）、可读性（业务语义化）、协作（多人并行开发不同页面）。PO 不写断言，断言在用例层。

**Q: 元素定位不到怎么办？**
① 看失败截图确认页面状态 ② 检查定位器是否失效（页面改版）→ 用语义化定位器 ③ 检查是否 iframe/shadow DOM ④ 显式等待是否足够 ⑤ 结合 console 日志。

**Q: 如何解决用例偶发失败（flaky）？**
定位根因分类：时序（→显式等待）、定位器脆弱（→语义化）、环境波动（→重试 1 次+截图证据）、共享状态（→隔离）。落地：重试+失败证据+flaky 识别区间+治理闭环。重试是"诊断工具"不是"长期方案"。

**Q: 测试金字塔是什么？**
底层单元测试（快、确定）→ 中层接口/契约测试（主力，80%）→ 顶层 UI E2E（少而精，只覆盖核心用户旅程）。UI E2E 维护成本最高，应下移断言到 API 层。平台看板有金字塔可视化。

**Q: 如何保证自动化项目可维护？**
分层架构 + 数据驱动 + 配置分离 + 失败证据 + flaky 治理 + 指标度量（通过率/flaky 率/MTTR）+ 定期重构（重复代码收敛）。

**Q: AI 时代测试开发做什么？（加分题）**
不止写脚本：搭质量平台（执行/度量/门禁）、AI 工具链（失败智能归因/用例生成/flaky 识别）、接口优先 + 左移、CI 门禁卡发布。本项目 AI 工具链（LLM 归因+规则降级）与质量平台就是该形态的落地。

## 5. CI/CD

- `pre-release-test.yml`：UI 测试 + API 测试 + Allure 报告 → GitHub Pages
- `post-release-validation.yml`：生产验证 + Locust 压测
- 端能力开关：`ENABLE_ANDROID=1` 等环境变量控制收集（conftest `pytest_ignore_collect`）
- 门禁语义：通过率/flaky 阈值在平台 `platform_config.yaml` 可配
